## One flaw wearing three hats

[Issue #10](https://github.com/TheOrcDev/shadscan/issues/10) reported
three unrelated-looking failures in a TanStack Start app. They turned out
to be one problem: each rule searched for its evidence inside a single
lexical scope. That works for code written the way the rule's author
pictured it, and fails the moment the implementation is composed — a
shortcut registered by a library, a button owned by a shared form, a
sidebar split across two modules. All three apps worked. Shadscan just
could not see it.

The reporter was right on every count, and their write-up was precise
enough to reproduce from directly.

## Shortcuts you did not write by hand

`theme-hotkey-present` used to insist on a raw `keydown` listener with a
literal key comparison and hand-rolled guards against typing targets. A
one-line `useHotkey("Mod+Shift+D", …)` had none of those things and
failed.

It now recognizes declarative registrations from
`@tanstack/react-hotkeys` and `react-hotkeys-hook`, resolved through the
import so a local hook that happens to share the name does not qualify.

The interesting part is the guard. Both libraries can ignore keystrokes
typed into inputs, and they express it with **opposite polarity**.
TanStack has `ignoreInputs`, whose default depends on the shortcut
itself — on for bare keys and Shift/Alt combos, off for Ctrl/Meta ones,
which is exactly why the reported `Mod+Shift+D` passes it explicitly.
`react-hotkeys-hook` has no such option; it ignores form tags by default
and only stops when you opt out with `enableOnFormTags`. A single matcher
would have rejected every correct usage of the second library, so each is
evaluated on its own terms.

A key spec that is not a static literal, or options hidden behind an
identifier, still fails. The rule reports what it can prove.

## Pending state that lives one component away

A shared form component that owns its submit button is good design and
used to score badly. The call site had the pending flag; the disabled
attribute and the spinner were one component down; the rule wanted all
three together.

It now follows a pending value through JSX props into the component that
receives it, across at most two boundaries, tracking renames along the
way — `isPending` handed down as `busy` is still the same value. Spread
props, external or unresolvable targets, ambiguous exports and computed
expressions all end the chain instead of being assumed sound, and when
the chain ends the failure says where.

## The sidebar the CLI actually generates

`mobile-nav-present` required `<SidebarProvider>`, `<Sidebar>` and a link
in one file. Nobody writes that. `shadcn add sidebar` nudges you toward a
provider in the root layout and a `<Sidebar>` in `app-sidebar.tsx`, which
never matched — so working mobile navigation was flagged.

The provider mount and the sidebar composition are now looked up
separately and then linked by resolving what the provider renders, which
keeps the check honest: an `app-sidebar` module that nothing mounts, or
one rendered outside the provider, still fails.

Burn-in against real projects then caught a second layer of the same
mistake. Requiring a link next to `<Sidebar>` was the single-file
assumption again, one level down — real sidebars hold a nav component,
and the nav component holds the links. The rule now reaches one hop
further.

## What this does to your score

These three rules are worth twelve points between them, so a project
using these idioms will score higher after upgrading without changing a
line. That is the bug being fixed, not a rescoring — but a number moving
on its own deserves an explanation.

Every change here loosens a rule, which inverts the usual risk: the
danger is passing an app that does not work, not failing one that does.
Four public projects were audited before and after. Exactly one status
changed, and it was checked by hand, end to end, before shipping.

## Also in this release

Module resolution had been reimplemented in five places. The rules that
need it now share one implementation, and the confined TypeScript host
and compiler options are built once per project instead of once per rule.
