## The dead end

Point shadscan at a monorepo root and it used to say "the nearest package
does not declare React" and stop. The root of a workspace almost never
declares React — that is what makes it a root. So the tool refused to
audit precisely the repository layout that `shadcn init --monorepo`
scaffolds.

It now walks the tree, finds every React application, audits each one, and
pools the findings into a single score. Discovery works the same way for
pnpm, npm, yarn, bun, Turborepo, Nx and Lerna, because it looks for
`package.json` files rather than parsing each tool's own workspace
configuration. That also means no YAML parser was added to a CLI that
ships six runtime dependencies.

## Why your design system is not in the score

This is the decision the feature rests on.

Audit a component library on its own and it scores badly — around 40, with
the whole foundation category at zero. Not because it is bad, but because
it has no page title, no favicon, no theme provider and no document shell.
It should not have any of those. Pool that into a monorepo's score and
every repository with a `packages/ui` takes a hit for owning a design
system. "My score dropped because my component library has no favicon" is
the kind of result that makes people stop trusting a number.

So packages are classified. Applications feed the score. Libraries are
still scanned and still reported with their own score — their
accessibility findings are genuinely useful — but they stay out of the
headline figure, and the report says so in as many words.

The signal that decides it is an application entry point, not a `main` or
`exports` field in the manifest. The first draft used the manifest and got
it backwards on real repositories, where internal packages are consumed
straight from source through a path alias and declare no entry at all.
Every application has an entry point, so its absence is the half of the
test that can be relied on.

## A number you can take apart

A pooled score that silently means something new is worse than no score at
all, so the report shows its working. Every package appears with its own
score, adapter and the reason it was classified the way it was — worst
first, because that is the one you want to read. Libraries sit in their
own labelled block. Packages that could not be audited are listed with the
reason.

`--list-projects` prints all of that without scanning anything, which is
the right tool when the classification surprises you, and `--project
apps/web` narrows a run to a single package.

A workspace holding one application at the repository root still takes the
old single-package path, so the common "app at the root with shared
packages beside it" layout keeps exactly the score it had.

## Proven against real repositories

`dub` pools to 21 — precisely the score its `apps/web` reported on its
own, since it is the only application there. `shadcn-ui/ui` pools eleven
applications into 40, and its `apps/v4` still reports the 34 it always
has. Scanning that repository first turned up 31 "projects", most of them
test fixtures describing real frameworks; discovery now skips the same
directories the scanner already refuses to read source from.

All nine framework adapters were re-scanned against the previous release
on identical inputs. Every score matched.

## Also in this release

`no-nested-interactive-controls` no longer reports a false positive for
Base UI's `render` composition. `<Button render={<Link />}>` passes the
link through the owner's attributes and renders it instead of the owner's
own tag, so exactly one anchor reaches the DOM — but the JSX walker saw a
link inside an interactive element and flagged it.

## For JSON consumers

The report schema is version 9. Findings, agent actionables and agent work
items gain `packageDir`; the report gains `workspace`, which is null for
single-package scans; and `framework.adapter` accepts `mixed` when pooled
applications use different frameworks. The GitHub Action reads `score` and
`grade` and needs no change.
