## Knowing when not to claim a project

React Router runs three ways. In declarative mode it is a `<BrowserRouter>`
inside an ordinary Vite SPA. In data mode it is `createBrowserRouter` with
loaders, still a SPA. Only in framework mode does it own the document, the
routes, and the server — and only that mode has conventions worth auditing
differently.

That distinction drove the design. The `react-router` package sits in a
very large number of ordinary React apps, so detecting on it alone would
have quietly reclassified them all. Detection instead requires three things
together: the dependency, a framework marker (`@react-router/dev` or a
`react-router.config` file), and an `app/root` module. Projects that have
only some of those keep the adapter they had, and the test suite pins that
behavior rather than trusting it.

## Sharing a directory name with Next

Framework mode keeps its code in `app/` — the same name Next's App Router
uses, and a directory shadscan already tracked. Overloading that field
would have coupled two frameworks through one value and made every rule
that reads it ambiguous. React Router gets its own paths instead, filled in
only when that adapter actually wins detection. A Next project that happens
to contain an `app/root.tsx` still audits as Next, and a React Router
project is never judged against Next's file conventions.

## Rules that speak the framework

The document shell is `app/root.tsx`: language, theme provider, toast
mounting, and — because framework mode renders on the server by default —
hydration safety. Metadata comes from the route `meta` export. Not-found
coverage is satisfied by an `ErrorBoundary` that handles
`isRouteErrorResponse` or by a splat route. Error handling recognizes the
`ErrorBoundary` export instead of asking for a component library. Routes
that export a loader need pending UI, satisfied by `HydrateFallback`,
`useNavigation` state, or a Suspense fallback — and resource routes, which
return data rather than markup, are left out of that entirely.

The render graph seeds one surface per route module, read from
`routes.ts` when its entries are literal and from directory discovery
otherwise, saying so in the report when it falls back. `ErrorBoundary` and
`HydrateFallback` exports become surfaces of their own; they render on real
navigations and were invisible until now.

## Burned in, and clean

Three public projects were audited before release: the official React
Router template, a real authentication app, and a declarative-mode SPA
kept as a control. All three classified correctly, the control stayed
where it belonged, and repeated runs matched exactly. Nothing needed
fixing — the first adapter of the recent four where the burn-in found no
false positives, which is what you would hope for from the one whose files
were ordinary TypeScript all along.

## One note for JSON consumers

The report schema is now version 8: `framework.adapter` accepts
`react-router-framework`, and `versions` includes `reactRouter`. The GitHub
Action reads `score` and `grade` and needs no change.
