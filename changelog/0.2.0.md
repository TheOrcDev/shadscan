## Recognized as itself

Until now, a TanStack Start app landed on the generic React adapter. Nothing
failed loudly — the audit simply skipped the checks that had no Next.js
equivalent, and the score came back thinner than it should have been.

Start apps are now detected from the `@tanstack/react-start` dependency
together with a `src/routes` or `app/routes` directory, checked before the
Vite adapter since Start builds on Vite. Projects that use TanStack Router
without Start stay where they were, and say so in their evidence.

## Rules that speak Start

Framework-aware rules learned Start's conventions rather than approximating
them. Metadata is read from the `head()` route option, not a Next export.
Not-found coverage comes from `notFoundComponent` or the router's
`defaultNotFoundComponent`. Loading coverage is required for loader-backed
routes and satisfied by `pendingComponent`. Because Start renders on the
server by default, the theme-hydration check now applies — and it looks for
`suppressHydrationWarning` in the root route's shell, where the `<html>`
element actually lives.

## The whole app, not just the entry

The component render graph seeds one surface per route file, expanding each
route's statically resolvable component options. Anatomy, navigation, and
composition rules see every route instead of whatever a single client entry
reached. Where composition can't be proven — an `<Outlet />`, an inline
arrow component — the graph records an explicit boundary reason instead of
guessing.

## One note for JSON consumers

The report schema is now version 5: `framework.adapter` accepts
`tanstack-start`, and `versions` includes `tanstackStart`. If you validate
`schemaVersion` strictly, accept 5. The GitHub Action reads `score` and
`grade` and needs no change.
