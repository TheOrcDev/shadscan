## A format we do not parse

Every adapter before this one kept its pages in TSX. Astro does not: the
routes, the layouts, and the `<html>` element all live in `.astro` files,
and the React components are islands mounted inside them. Auditing the
islands without reading those files would mean seeing the components and
missing the page.

So shadscan reads them, along one deliberate line. The frontmatter — the
TypeScript between the `---` fences — is parsed with the same TypeScript
parser every other file gets, because it is TypeScript, and because it is
the only reliable way to know which components a page imports. The
template below the fences is treated as text. No template AST, no
attempt to understand conditional rendering. Where composition cannot be
proven, the report records a boundary reason instead of guessing.

## What that buys you

Document rules now read your Astro layouts: the `lang` attribute, the
title and description, the favicon link, Open Graph images, and
`src/pages/404.astro`. Layouts are found by content rather than by
convention, so it does not matter where you keep them.

The component render graph seeds one surface per `.astro` page or layout,
rooted in the islands that file imports and renders — whether they carry
a `client:*` directive or render on the server. Toast and theme-provider
mounts trace from the layout into the island component, including
islands imported straight from a package.

## Found by running it on real sites

Before release, the adapter ran against three public Astro projects
spanning Astro 4 through 7. Two false positives turned up that fixtures
would never have shown: Astro passes metadata as expressions
(`content={description}`), which the HTML patterns had been rejecting,
and a toaster imported directly from its package in frontmatter was
invisible to the mount trace. Both are fixed, with tests. One of those
sites went from 45 to 64 once the audit stopped being wrong about it.

## A quiet fix for Laravel too

Chasing the Astro work surfaced that hosted web scans were discarding
`.astro` templates during extraction — and had been discarding Laravel's
Blade views since 0.3.0. Scanning either stack through the web scanner
reported generic React. Both are retained now; local CLI scans were
never affected.

## One note for JSON consumers

The report schema is now version 7: `framework.adapter` accepts
`astro-react`, and `versions` includes `astro`. The GitHub Action reads
`score` and `grade` and needs no change.
